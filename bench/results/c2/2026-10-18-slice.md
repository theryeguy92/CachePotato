# C2 slice — the decode measurement protocol, run once to validate it

**Date:** 2026-10-18 · **Branch:** `feat/qwen3-30b-a3b` · **Status: protocol validation, not a result.**

The point of this run was to find out whether the instrument works before spending two hours
producing numbers with it. It did, after two defects were fixed — and the first measurement also
falsified the prediction that was written down before the run, which is the other reason to do a
slice first.

## What was run

Qwen3-30B-A3B Q8 (32.5 GB) on the T480 (16 GB), prompt p0 (5 tokens), **8 greedy tokens decoded one
at a time against a KV cache**, no sampling. `tools/c2_measure.py`, raw output beside this file.

| config | what it is |
|---|---|
| `control` | `CP_PAGER=1`, no budget: the pager counts, never evicts → the OS page cache with instrumentation. This is the unpaged run. |
| `b8192` | `CP_PAGER=1 CP_BUDGET=8192` |
| `b8192sys` | as above + `CP_PAGER_SYS=1`: evicted regions are also dropped from the system page cache, so a miss is a real disk read |

## What the slice validates

1. **The decode path is prefill, bit for bit.** `tools/verify_qwen3_decode.py` (now gate 19):
   decode logits are byte-identical to prefill's at positions 4–11, and prefill's argmax reproduces
   the generated chain exactly. The regions/token table therefore describes a verified path.
2. **The two instruments agree.** At `CP_PAGER_SYS=1`, 562 MB fetched vs **624 MB physically read**
   per token — the 11% excess is read granularity/readahead around a 5 MB region, not an accounting
   gap. With the system cache left alone the same run reads only **166 MB**: the page cache masks
   86% of the pager's misses. That is the number that would have been reported as a 6.8× win if only
   the logical counter had been used. **`CP_PAGER_SYS=1` is the headline column.**
3. **The per-token table closes on an independent expectation.** Every generated position logs
   regions + hits = **819** — 48 layers × (9 core + 8 experts) + embed, plus the final norm and head
   charged to the position whose logits they produce. A shifted or truncated row cannot look
   plausible.
4. **Core residency behaves exactly.** Core: 5,645 accesses, 5,210 hits → **435 misses = the number
   of core regions in the file**. Every core region was fetched once and never evicted, at 8 GB,
   which is what the budget arithmetic says should happen.

## The prediction was wrong, and that matters

Written down before the run: *"at 128 experts selecting 8, uniform reuse is 6.25% per slot, so
expect expert hits to be low and regions fetched per token to be nearly flat across budgets."*

Measured at 8 GB: **384 experts demanded, 112 fetched → 71% of a token's experts are already
resident.** Consecutive tokens share experts far more than a uniform router would, which is exactly
what a trained router is supposed to do. So:

- the uniform-selection model must **not** be used to size budgets or to predict hit rates;
- the budget is not the main lever at 8 GB — reuse is — which sharpens the Tier-B question rather
  than answering it (grouping co-selected experts is now motivated by *measured* co-selection, not
  by an assumption).

## Two defects found by running it, before any number was trusted

1. **Off-by-one in the measuring script.** It read the pager row for position `pos+1` and
   zero-filled the last row, shifting every per-token number and silently dropping one. Caught by
   the 819-touch assertion, which is now in the script permanently.
2. **The driver segfaulted on an output path whose directory did not exist** (`fopen` unchecked,
   `fwrite` to NULL). A run that computes for a minute and then dies without saying why is worse
   than one that refuses to start; every output `fopen` is now checked.

## What is deliberately not claimed here

The `control` row is **not** yet a clean pager-vs-OS comparison. `control` ran first, with whatever
page-cache state the preceding gate left; the budgeted runs ran after it; each config ran **once**;
and 8 tokens is long enough for the transient to matter. The 1355 vs 624 MB/token gap (2.2×) is
therefore *suggestive, not a result*.

A time model that fits the two ends loosely: `t ≈ 4.3 s compute + physical MB / 0.39 GB/s`. The
`sys=1` and control rows fit within 5%; `b8192` is ~15% slower than the fit predicts, i.e. a
page-cache "hit" is not free.

## The full matrix must fix, before any budget table is published

- **cold start per config** — drop every page of the model file before each run (`posix_fadvise`
  on our own fd needs no privileges), so "cold" is a property of the run, not of what ran before it;
- **interleave and repeat** configs (n ≥ 5) and compare paired, as `tools/ab.py` does — cache
  history and the T480's 3100→2593 MHz throttling both exceed the effect being measured;
- **32+ tokens** so the steady state dominates the first-token transient, and report the prefill
  separately from the decode loop;
- **watch the core hit rate collapse** at 2 GB and 4 GB: core is 1.6 GB of a 2 GB budget, so anchor
  thrash must be read before the expert numbers are interpreted (and it is the trigger for the
  core-pinning decision, which is deliberately deferred until those numbers exist);
- record the machine stamp with the table (`<prefix>.meta` already does this).
